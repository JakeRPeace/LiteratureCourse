# Course Data Pipeline Plan

## Goal
- Enable chatbot-driven course creation by moving course data from Markdown into Supabase.
- Keep Markdown as the source for system courses during migration.

## Scope (Phase 1: Data Pipeline)
In scope:
- Define a Supabase schema for courses, books, docs, guides, and summaries.
- Build a repeatable import pipeline from Markdown to Supabase.
- Track sync metadata to detect changes and avoid unnecessary re-imports.

Out of scope (later phases):
- Chatbot UX, prompt design, and course-generation logic.
- Full UI refactor to replace all Markdown reads.
- Course sharing and collaboration features.

## Current State
- Course content lives in the repo under Johnny.Decimal folders.
- `site/src/lib/content.js` parses Markdown at runtime for the site.
- Supabase currently stores `book_status` only.

## Implementation Notes (Current)
- `site/scripts/sync-content-to-supabase.mjs` writes system rows and skips when the repo manifest checksum is unchanged; use `--force` to resync.
- `site/scripts/verify-supabase-content.mjs` runs during build and fails deploy if system rows drift from Markdown.
- Frontend now prefers Supabase for system courses/books/docs/guides with Markdown fallback.
- Build-time sync requires `SUPABASE_SERVICE_ROLE_KEY` (server-only).

## Operational Constraints
- Avoid editing system rows directly in Supabase unless the Markdown source is updated too.
- `content_sync` is service-role only; keep it that way to prevent client access.

## Target Data Model (Draft)
- `courses`
  - `course_id` (text, e.g. `10-19`)
  - `title` (full course title)
  - `course_type` (literature type, e.g. `Modern Literature`)
  - `summary` (short recap)
  - `slug`
  - `status` (optional, display-only)
  - `source` (`system` or `user`)
  - `owner_id` (nullable, for user-created courses)
  - `created_at`, `updated_at`
- `course_docs`
  - `course_id`, `doc_type`, `label`, `stage`, `content_md`, `excerpt`, `order`
- `course_categories`
  - `course_id`, `name`, `order`
- `books`
  - `book_id` (text, e.g. `10-19/11.01 ...`)
  - `course_id`, `category`, `title`, `author`, `slug`
  - `cover_url`, `cover_source`, `order`
- `book_guides`
  - `book_id`, `guide_type`, `label`, `stage`, `content_md`, `excerpt`, `order`
- `content_sync`
  - `source` (`md`), `source_path`, `checksum`, `synced_at`

RLS defaults:
- `system` rows are read-only.
- `user` rows are read/write for `owner_id`.

## Decisions
- User-created courses are private and tied to `owner_id`.
- System courses are read-only; users can only edit status, score, and future notes.
- Store full Markdown for course docs and guides.
- Covers are fetched on app load; on creation, fetch then cache in DB.

## Ingestion Pipeline
1. Extract
   - Parse Markdown with existing logic (frontmatter, excerpts, ordering).
   - Normalize fields (IDs, slugs, course type).
2. Transform
   - Derive stable IDs from folder names.
   - Map course overview into `summary`.
3. Load
   - Upsert in dependency order: courses -> categories -> books -> docs -> guides.
   - Store checksums in `content_sync` to skip unchanged content.
4. Verify
   - Compare counts vs repo (courses, books, docs).
   - Spot-check excerpts and slugs.

## Migration Strategy
- Create a script: `site/scripts/sync-content-to-supabase.mjs`.
- Run a one-time full import, then re-run on content updates.
- Update frontend to read Supabase first and fall back to Markdown until parity.

## Chatbot-Ready Additions (After Pipeline)
- Allow inserts into `courses`/`books`/`course_docs` with `source="user"` and `owner_id`.
- Store conversation logs and draft course payloads if needed.
